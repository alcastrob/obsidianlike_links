# CLAUDE.md

Guía para Claude Code al trabajar en este repositorio.

## Qué es este proyecto

Extensión de VS Code (TypeScript) que replica funcionalidades de Obsidian basadas en wikilinks `[[nota]]` sobre archivos Markdown: autocompletado, navegación, hover preview, y un panel lateral tipo Obsidian (barra de iconos + contenido a pantalla completa) con 5 herramientas: Enlaces entrantes, Enlaces salientes, Etiquetas, Propiedades y Esquema.

## Comandos

```bash
npm install        # instalar dependencias
npm run compile     # compilar TypeScript (tsc -p ./)
npm run watch        # compilar en modo watch
npm run lint          # eslint sobre src/
```

Para probar manualmente: abrir el proyecto en VS Code y pulsar `F5` (task `npm: compile` se ejecuta como `preLaunchTask`, ver `.vscode/launch.json`). Esto abre una ventana "Extension Development Host"; abrir ahí una carpeta con `.md` que use `[[wikilinks]]`.

No hay suite de tests automatizada todavía (el script `test` referencia `./out/test/runTest.js`, que aún no existe).

## Arquitectura

- `src/wikilinks.ts` es el módulo base de wikilinks: regex (`WIKILINK_REGEX`), búsqueda de notas en el workspace (`findNoteFiles`), resolución de nombre → archivo (`resolveNoteFile`), y extracción de wikilinks de un texto (`extractWikilinksDetailed`, distingue transclusiones `![[nota]]` de enlaces normales). Todo lo relacionado con enlaces depende de este módulo — si cambias el formato de wikilink soportado, hazlo aquí primero. `wikilinkTargetName(rawName)` normaliza el destino de un wikilink al nombre de nota resoluble: Obsidian admite `[[carpeta/nota]]` y `[[carpeta/nota.md]]` además de `[[nota]]`, pero la resolución aquí es por nombre de archivo sin extensión, así que descarta el directorio y una extensión final solo si está en `obsidianlikeLinks.noteExtensions` (para no partir notas con puntos en el nombre como `v1.2 apuntes`). Úsalo en cualquier sitio que compare o resuelva el `noteName` de un wikilink — `resolveNoteFile` ya lo hace, y `computeBacklinks` en `toolData.ts` también.
- `src/markdownUtils.ts` es el módulo base para tags/frontmatter/encabezados: `extractTags`, `extractFrontmatterKeys`, `extractHeadings`. Todos ignoran el contenido dentro de bloques de código ` ``` ` (ver `stripFencedCodeBlocks`). `extractTags` usa `TAG_REGEX` con `\p{L}`/`\p{N}` (flag `u`) en vez de `\w`, para que etiquetas con acentos (`#documentación`, `#económico`) no se trunquen en la primera letra no-ASCII — `\w` de JS solo cubre `[A-Za-z0-9_]`. También descarta como etiqueta cualquier match cuyos ~30 caracteres previos al `#` terminen en una declaración CSS `...color:` (`CSS_COLOR_BEFORE_HASH`), porque un código de color hex como `background-color:#e3ff00;` (del highlight de la extensión hermana `obsidianlike`) tiene la misma forma que una etiqueta válida y no debe tratarse como tal.
- `src/providers/` implementa las interfaces estándar de la API de VS Code (`CompletionItemProvider`, `DefinitionProvider`, `HoverProvider`), registradas en `extension.ts` para el selector de lenguaje `markdown`.
- `src/activeMarkdownDocument.ts` (`ActiveMarkdownDocumentTracker`) resuelve el documento Markdown de la **pestaña activa**. **No uses `vscode.window.activeTextEditor`** para esto: pasa a `undefined` en cuanto el foco sale de un editor de texto (incluido hacer clic en nuestro propio panel), y si el archivo ya estaba abierto/activo antes de que la extensión se active nunca llega un evento de cambio para él. En su lugar usa `vscode.window.tabGroups.activeTabGroup.activeTab`, que no depende del foco — y acepta cualquier tipo de pestaña con una `uri` (`TabInputText`, `TabInputCustom`, `TabInputNotebook`), no solo editores de texto plano: en esta "Obsidian like" profile, otra extensión hermana registra un editor personalizado para `.md`, así que las pestañas de nota suelen ser `TabInputCustom`, no `TabInputText`. `getDocument()` es async (usa `openTextDocument`, que no compara URIs a mano). Si vuelve a fallar la detección, `describeActiveTab()` da diagnóstico y `postData()` en `panelViewProvider.ts` lo añade al `emptyMessage` — mira eso antes de re-teorizar.
  - **`vscode.window.tabGroups.onDidChangeTabs`/`onDidChangeTabGroups` no son fiables en timing** con el editor personalizado de la extensión hermana `obsidianlike` (`vaultTool.markdownEditor`): a veces disparan dos eventos en ~50ms donde el segundo lee la pestaña VIEJA como activa (sin un tercer evento que corrija), y a veces se retrasan varios segundos respecto al cambio visual de pestaña — este segundo caso resultó ser un bug real en `obsidianlike` (ver su propio `CLAUDE.md`, sección "Autosave": cambiar de pestaña marcaba la nota como sucia y disparaba un autoguardado aunque no hubiera edición, y ese ciclo de guardado es lo que retrasaba el evento), ya corregido allí, pero el tracker no debe depender de que esa u otra extensión hermana se comporte bien. Por eso `checkActiveTab()` no reacciona a cada evento tal cual: los eventos programan una relectura tras `TAB_SETTLE_DELAY_MS` (150ms, deja que el parpadeo se asiente) y, como red de seguridad adicional, un `setInterval` de `POLL_INTERVAL_MS` (400ms) sondea la pestaña activa directamente sin depender de que el evento llegue. Ambos caminos convergen en `checkActiveTab()`, que solo dispara `onDidChange` si la uri resuelta difiere de la última notificada (dedupe por `lastNotifiedKey`).
  - Todo esto se depuró correlacionando el canal de salida `log.ts` ("Obsidian-like Links", ver `View > Output`) con vídeo grabado de la reproducción — comparar fotograma a fotograma qué pestaña estaba realmente activa contra qué decía el log en ese instante fue lo que reveló que el cálculo del lado de la extensión siempre era correcto y el problema estaba en el timing de los eventos de VS Code, no en nuestra lógica.
- `src/log.ts` expone un `vscode.OutputChannel` compartido ("Obsidian-like Links", visible en `View > Output`) y una función `log()` con timestamp. Lo usan `activeMarkdownDocument.ts`, `panelViewProvider.ts` y `extension.ts` para dejar rastro de cada evento de cambio de pestaña, cada `postData()` (con la etiqueta de los nodos calculados y un preview del texto del documento) y cualquier error — fue clave para diagnosticar el bug de detección de pestaña activa documentado arriba, y sigue siendo el primer sitio donde mirar ante cualquier reporte de "el panel no se actualiza" o "muestra datos de otro documento".
- `src/toolData.ts` (`computeToolData`) calcula los datos de las 5 herramientas y los devuelve como `TreeNode[]` (definido en `src/treeNode.ts`) — una estructura serializable en JSON, sin nada de la API de VS Code, para poder enviarla a un webview por `postMessage`. Enlaces entrantes/salientes y Esquema dependen del documento activo (via el tracker); Etiquetas y Propiedades escanean toda la bóveda y son planas (sin `children`): un `TreeNode` puede llevar `searchQuery` en vez de `uri`, y en ese caso un click no abre un archivo sino que dispara una búsqueda (ver siguiente punto). Enlaces salientes excluye transclusiones de imagen (`![[foo.png]]`, ver `isImageFilename`/`IMAGE_EXTENSIONS`) — solo interesan las transclusiones de notas.
- `src/views/panelViewProvider.ts` implementa `WebviewViewProvider` para el único view del panel (`obsidianlikeLinks.panelView`, `"type": "webview"` en `package.json`). El HTML/CSS/JS del webview vive inline en ese mismo archivo (sin bundler): la barra de iconos superior selecciona la herramienta (mensaje `selectTool` → recalcula con `computeToolData` → `postMessage` de vuelta) y el árbol se renderiza recursivamente ocupando el resto del alto. En el árbol, solo el twisty (flecha) colapsa/expande (con `stopPropagation` para no disparar también la navegación); un click en el resto de la fila de un nodo con `uri` envía `{type:'open', uri, line}` (ver `openNote()` más abajo) sin importar si el nodo tiene hijos o no; un click en un nodo con `searchQuery` (Etiquetas/Propiedades) envía `{type:'search', query}`, que el host reenvía como comando `obsidianlikeSearch.searchFor` a la extensión hermana `obsidianlike_search` (soft dependency: comprueba con `vscode.commands.getCommands` antes de ejecutar, y avisa si no está instalada). No hay TreeDataProvider/TreeView nativos de VS Code — se sustituyeron a propósito porque el usuario quería una barra de herramientas propia en vez del apilado estándar de vistas de VS Code.
  - `openNote(uri, line)` (usado por el handler de `{type:'open'}`) **no puede usar `vscode.open` con `selection` para hacer scroll**, porque las notas se muestran con el editor personalizado `vaultTool.markdownEditor` de la extensión hermana `obsidianlike` (ver `activeMarkdownDocument.ts`), y `selection` solo lo interpreta el editor de texto plano nativo (hace `revealRange` sobre un `TextEditor`, que no existe para un editor basado en webview). En su lugar delega en el comando `vaultTool.openNoteAtLine(uri, line)` de esa extensión (soft dependency: comprueba con `vscode.commands.getCommands` antes de ejecutar) y solo cae a `vscode.open`+`selection` si esa extensión no está instalada. `line` es 0-based en ambos casos — coincide con `heading.line` de `markdownUtils.ts` y con lo que espera `vaultTool.openNoteAtLine` (hace `doc.line(line + 1)` internamente, ver `webview-src/editor.js` de `obsidianlike`). Esta comprobación previa con `getCommands()` es fiable aquí porque `obsidianlike` ya está activa siempre que se use este panel (es la extensión que renderiza la nota actual) — no asumas lo mismo para otras soft dependencies, ver `runSearch()` justo abajo.
  - `runSearch(query)` (handler de `{type:'search'}`, dispara la búsqueda de tags/propiedades) **no comprueba `getCommands()` antes de ejecutar** `obsidianlikeSearch.searchFor`, a diferencia de `openNote()`: la extensión hermana `obsidianlike_search` no tiene por qué estar ya activada (su vista puede no haberse abierto nunca en la sesión), y `getCommands()` puede no reflejar todavía un comando de una extensión contribuida-pero-no-activada — comprobarlo antes producía un falso "La extensión Obsidian-like Search no está instalada" con la extensión instalada y al día. Ahora se ejecuta `executeCommand` directamente (que sí activa la extensión bajo demanda) dentro de un try/catch, y solo se avisa al usuario si la ejecución falla de verdad (el mensaje de error se inspecciona con `/command.*not found/i` para distinguir "no instalada" de un fallo interno de esa extensión, que se reporta con un mensaje distinto y se registra en `log.ts`).
  - `postData()` está protegido contra condiciones de carrera: cada llamada obtiene un `requestSeq` incremental y, si al terminar de calcular ya no es la última petición en curso (llegó un refresco más nuevo mientras esta calculaba), se descarta en vez de enviarse al webview y pisar datos actuales con datos obsoletos. Todo el cuerpo va envuelto en try/catch — antes, una excepción dentro de `postData()` (llamada como `void this.postData()` desde `refresh()`, sin `.catch`) se perdía como promise rejection silenciosa: el panel se quedaba con los últimos datos válidos sin ningún indicio de que algo había fallado. Ahora cualquier error se registra en `log.ts` y también se muestra en el propio panel (`emptyMessage` con referencia al canal de salida).
- **Integración cruzada con `obsidianlike_search`** (repo hermano, `D:\git\obsidianlike_search`): el comando `obsidianlikeSearch.searchFor(query: string)` (en `src/extension.ts` de ese repo) revela su view container y llama a `SearchViewProvider.runQuery(query)`, que hace `postMessage({command:'setQuery', query})` al webview de búsqueda (`media/main.js`, handler `setQuery`) — con handshake `pendingQuery`/`webviewReady` para no perder el mensaje si el webview aún no había cargado. La query usa la sintaxis del motor de búsqueda de ese repo (`src/searchEngine.ts`): `tag:valor` para etiquetas, `[clave]` para propiedades de frontmatter. Si cambias esa sintaxis allí, actualiza `toolData.ts` (`computeTags`/`computeProperties`) aquí.
- `src/extension.ts` es el único punto donde se registran providers, el webview view y comandos (`activate`). Mantener este patrón: no registrar nada fuera de `activate`/`deactivate`.
- La resolución de notas es por **nombre de archivo sin extensión**, sin distinguir mayúsculas/minúsculas (comportamiento estilo Obsidian). Un wikilink con directorio (`[[carpeta/nota]]`) o con extensión (`[[nota.md]]`) se acepta pero se colapsa a su nombre base vía `wikilinkTargetName` — no hay soporte aún para desambiguar por ruta ni para notas con nombres duplicados en distintas carpetas — si se añade, debe seguir viviendo en `wikilinks.ts`.
- **ESLint**: usa flat config (`eslint.config.mjs`), no `.eslintrc.*` — el `package.json` de este proyecto fija `eslint@^10.8.0`, que requiere config plano. El script `lint` pasa `--no-color`: sin ese flag, el formateador `stylish` por defecto llama a `util.styleText`, que no existe en Node < 20.12 y revienta con `TypeError: util.styleText is not a function` aunque no haya errores de lint — es un problema del entorno/versión de Node, no del código.

## Convenciones

- La UI visible para el usuario (títulos de comandos, nombres de vistas, mensajes) está en español, siguiendo el idioma en que se definió el proyecto. El código (identificadores, comentarios) está en inglés/neutro salvo los textos de usuario.
- Contribuciones nuevas de comandos/vistas van en `package.json` bajo `contributes`, y deben registrarse correspondientemente en `activate()`.
- El icono de la extensión (Marketplace / vista de extensiones instaladas) es `package.json` → `icon`, apuntando a `media/obsidian-icon-violeta.png` (128×128). Es distinto del icono de la barra de actividad (`contributes.viewsContainers.activitybar[0].icon`, `media/icon.svg`) — ese debe seguir siendo un SVG monocromo para que VS Code lo tematice junto al resto de iconos de la barra.
- Comentarios solo cuando el porqué no es obvio; no documentar lo que el código ya expresa.

## Monorepo hermano

Este proyecto es una de varias extensiones "Obsidian like" en repos hermanos bajo `D:\git\` (`obsidianlike`, `obsidianlike_calendar`, `obsidianlike_search`, `obsidianlike_tasks`, etc.). `D:\git\obsidianlike\make.bat` compila (`npm run package`, que corre `vsce package`), desinstala e instala cada una en el perfil de VS Code `"Obsidian like"`. Si cambias el `name` o `version` en `package.json`, actualiza el bloque correspondiente en ese `make.bat` (nombre del `.vsix` e id `angelCastro.<name>`).

Corregido (2026-07-26): el panel a veces mostraba enlaces entrantes/salientes del documento equivocado al cambiar de pestaña rápido. Causa real, en dos partes — ver detalle en `activeMarkdownDocument.ts` y `panelViewProvider.ts` arriba: (1) condición de carrera en `postData()` sin protección contra respuestas asíncronas fuera de orden, y (2) los eventos de VS Code sobre la pestaña activa no eran fiables en timing con el editor personalizado de `obsidianlike`, a su vez causado por un bug real en esa extensión (autoguardado espurio al cambiar de pestaña sin editar nada, ya corregido allí también). Se añadió `log.ts` (canal de salida) para poder diagnosticar este tipo de problema en el futuro sin depender de adivinar.

Corregido (2026-07-30): al pulsar una cabecera del Esquema no se hacía scroll a su posición en el documento. Dos causas, ver detalle en `panelViewProvider.ts` arriba: (1) en el webview, el click en una fila con hijos solo colapsaba/expandía y nunca navegaba (ahora solo el twisty hace eso, con `stopPropagation`); (2) `vscode.open` con `selection` no tiene efecto sobre el editor personalizado `vaultTool.markdownEditor` de `obsidianlike` (esa opción solo la interpreta el editor de texto plano nativo). Ahora `openNote()` delega el scroll en el comando `vaultTool.openNoteAtLine(uri, line)` de esa extensión cuando está instalada.

Corregido (2026-08-02): tres bugs reportados en el panel de Etiquetas y en la búsqueda cruzada:
- Pulsar una etiqueta mostraba "La extensión Obsidian-like Search no está instalada" aunque `obsidianlike_search` estuviera instalada y activa. Causa: `runSearch()` comprobaba `getCommands()` antes de ejecutar, y esa lista puede no incluir todavía el comando de una extensión contribuida pero aún no activada. Ver detalle en `panelViewProvider.ts` arriba.
- Las etiquetas con acentos se truncaban en la primera letra no-ASCII (`#documentación` → `#documentaci`). Causa: `TAG_REGEX` en `markdownUtils.ts` usaba `\w`, que en JS no incluye letras acentuadas; ahora usa `\p{L}`/`\p{N}` con flag `u`.
- Códigos de color hex usados por el highlight de `obsidianlike` (p.ej. `<mark style="background-color:#e3ff00;">`) se listaban como etiquetas por tener la misma forma. `extractTags` ahora descarta un match si justo antes del `#` hay una declaración CSS `...color:`.

Corregido (2026-08-28): un wikilink con directorio (`[[carpeta/nota]]`) no se contabilizaba como enlace entrante. Causa: `computeBacklinks` comparaba `link.noteName` en crudo contra el nombre del archivo activo, y `"carpeta/nota"` nunca igualaba `"nota"`. Se añadió `wikilinkTargetName` en `wikilinks.ts` (colapsa el destino a su nombre base, descartando directorio y extensión de nota final); lo usan ahora `resolveNoteFile` y `computeBacklinks`, así que los enlaces con directorio también resuelven para navegación, hover y Enlaces salientes.

Corregido (2026-08-28, 2): en una nota con acento en el nombre (`out/👶 José Javier Montes Romero (JJ).md`) el panel de Enlaces entrantes solo mostraba 1 de decenas de enlaces reales. Causa: mismatch de normalización Unicode — el nombre de archivo en disco venía en forma descompuesta (NFD, `e` + acento combinado, típico de archivos originados en macOS) y el texto de los wikilinks estaba en forma precompuesta (NFC), así que la comparación `toLowerCase() === toLowerCase()` fallaba aunque ambos se vieran idénticos; solo casaba el enlace que por casualidad estaba en la misma forma que el archivo. Se añadió `noteNameKey(name)` en `wikilinks.ts` (`name.normalize("NFC").toLowerCase()`, replicando que Obsidian normaliza todas las rutas a NFC); lo usan `resolveNoteFile` y `computeBacklinks` para todas las comparaciones de `noteName`. Si algún enlace concreto siguiera sin casar, mirar caracteres invisibles no reconciliables por NFC (selector de variación `U+FE0F` tras un emoji, `U+00A0` en vez de espacio).
